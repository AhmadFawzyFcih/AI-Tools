/analyze-requirements

Analyze

Fetches Jira user stories and Figma designs, maps them together, detects mismatches and gaps, then publishes a requirements analysis report to Confluence.

Single ticket

▶

Analyze a single Jira story. Figma links are auto-discovered from the ticket's description and attachments.

/analyze-requirements PROJ-123
→ requirements-analysis-2026-02-15.md + Confluence page

Multiple tickets

▶

Analyze several stories at once. Accepts space or comma-separated ticket IDs.

/analyze-requirements PROJ-123 PROJ-456 PROJ-789

Sprint

▶

Analyze all stories in a sprint by name.

/analyze-requirements "Sprint 5"

Tickets + Figma designs

▶

Provide Figma URLs explicitly when they're not linked in the Jira tickets.

/analyze-requirements PROJ-123 PROJ-456 \ --figma https://www.figma.com/design/abc/File1 https://www.figma.com/design/def/File2

Full example with linked tasks

Recommended
▶

The full command: multiple tickets, linked task inspection, and explicit Figma files. This gives the most thorough analysis.

/analyze-requirements PROJ-123 PROJ-456 \ --check-linked-tasks \ --figma https://www.figma.com/design/abc/File1
→ requirements-analysis-2026-02-15.md + Confluence page
FlagDescription
--figma <urls> One or more Figma file URLs to analyze against the Jira stories
--check-linked-tasks Also fetch linked issues, subtasks, priority, and status for each story

/plan-implementation

Plan

Gathers context from Jira, Confluence, and your initial thoughts, then produces a phased implementation plan covering edge cases, performance, and maintainability.

Full mode (first-time planning)

Full
▶

Create a brand-new implementation plan from Jira stories, a Confluence spec page, and your initial ideas.

/plan-implementation https://planradar.atlassian.net/browse/PROJ-123 \ --confluence https://planradar.atlassian.net/wiki/spaces/PMT/pages/123/Spec \ --thoughts "Queue-based approach with Redis"
→ implementation-plan-PROJ-123-2026-02-15.md

Multiple Jira tickets + Confluence pages

Full
▶

Pass multiple Jira URLs and Confluence specs for a larger feature spanning several stories.

/plan-implementation \ https://planradar.atlassian.net/browse/PROJ-123 \ https://planradar.atlassian.net/browse/PROJ-456 \ --confluence https://planradar.atlassian.net/wiki/spaces/PMT/pages/111/Page1 \ https://planradar.atlassian.net/wiki/spaces/PMT/pages/222/Page2 \ --thoughts "CQRS with separate read and write models"
→ implementation-plan-PROJ-123-PROJ-456-2026-02-15.md

Revision mode (mid-implementation changes)

Revision
▶

Something changed mid-implementation? Pass the existing plan file instead of a Jira URL. The command discusses the changes with you first, then creates a new revision file. Never overwrites the original.

/plan-implementation ./implementation-plan-PROJ-123-2026-02-15.md \ --thoughts "Bulk delete locks the table, need batched soft deletes instead"
→ implementation-plan-PROJ-123-2026-02-15-rev-1.md

The revision file works directly with /implement-plan to continue development.

FlagDescription
--confluence <urls> One or more Confluence page URLs containing feature specs
--thoughts <text> Your initial implementation ideas, constraints, or approach

/implement-plan

Build

Takes an implementation plan and executes it interactively — discusses architecture, then implements one phase at a time with code + tests, waiting for your approval before advancing.

Start implementation

▶

Point it to a plan file generated by /plan-implementation. The command reads the plan, walks through architecture decisions with you, then implements phase by phase.

/implement-plan ./implementation-plan-PROJ-123-2026-02-15.md

Continue from a revised plan

▶

After using /plan-implementation in revision mode, pass the new revision file to continue development with the updated plan.

/implement-plan ./implementation-plan-PROJ-123-2026-02-15-rev-1.md

Interactive Flow

1. Reads the plan and summarizes it
2. Architecture discussion — SOLID, MVC, service boundaries, design patterns, V2 APIs, file structure
3. Phase-by-phase implementation — code + RSpec tests + permissions check
4. Waits for your approval before moving to the next phase
5. Final summary of all files created/modified

/implement-plan-nicely

Build Dashboard

Identical to /implement-plan but generates and continuously updates a visual HTML progress dashboard — tracking phases, architecture decisions, file counts, spec results, and issues in real time.

Start implementation with dashboard

▶

Point it to a plan file generated by /plan-implementation. Before the architecture discussion even starts, it creates a live HTML dashboard you can open in a browser.

/implement-plan-nicely ./implementation-plan-PROJ-123-2026-02-15.md
→ implementation-progress-2026-02-15-143025.html

Continue from a revised plan

▶

After using /plan-implementation in revision mode, pass the new revision file. The dashboard tracks the revised phases.

/implement-plan-nicely ./implementation-plan-PROJ-123-2026-02-15-rev-1.md
→ implementation-progress-2026-02-15-160512.html

Interactive Flow (same as /implement-plan)

1. Reads the plan, summarizes it, and generates the HTML dashboard
2. Architecture discussion — SOLID, MVC, service boundaries, design patterns, V2 APIs, file structure
3. Phase-by-phase implementation — code + RSpec tests + permissions check
4. Waits for your approval before moving to the next phase
5. Final summary of all files created/modified

Dashboard Updates

✓ Complete ↻ In Progress ⏳ Pending ✗ Failed ⚠ Needs Attention

The dashboard is updated after every significant step: plan read, each architecture sub-discussion, each file created, each spec run, each phase completion. Refresh the browser to see the latest state.

/review

Review

Reviews code changes against a 10-point checklist (N+1 queries, security, SOLID, performance, etc.) and generates an interactive HTML report with categorized findings.

Local review (before commit)

Local
▶

Review all uncommitted changes. After generating the HTML report, you select which findings to fix by number.

/review
→ review-2026-02-15-143025.html

Local review with plan reference

Local
▶

Review changes and check if the implementation plan needs updating. After fixes, it asks whether to create a plan revision.

/review --plan ./implementation-plan-PROJ-123-2026-02-15.md

Remote review (GitLab MR)

Remote
▶

Review a remote Merge Request. Generates an HTML report — you select which findings to post as MR comments.

/review https://gitlab.com/planradar/project/-/merge_requests/123
→ review-mr-123-2026-02-15.html

Remote review (GitHub PR)

Remote
▶

Works the same with GitHub pull requests.

/review https://github.com/planradar/project/pull/456
FlagDescription
--plan <path> Path to the implementation plan file (local mode only). Enables plan revision check after applying fixes.

Review Checklist (10 categories)

N+1 Queries Performance Security SOLID Code Structure Syntax & Style Specs Coverage Backward Compat Error Handling Rails Best Practices

/documentation

Docs

Creates or updates Confluence API documentation by analyzing the codebase and the implementation plan. Includes endpoints, parameters, responses, cURL examples, and a changelog.

New page (create from scratch)

New
▶

Create a brand-new Confluence documentation page under a folder. Analyzes the code and the plan to document all API endpoints.

/documentation --new https://planradar.atlassian.net/wiki/spaces/PMT/folder/4040359987 \ ./implementation-plan-PROJ-123-2026-02-15.md \ --thoughts "Checklist field feature, covers CRUD and bulk operations"
→ New Confluence page created under the specified folder

Update existing page

Update
▶

Update an existing Confluence documentation page. Generates an interactive HTML review page showing a before/after diff — you choose which changes to apply.

/documentation \ https://planradar.atlassian.net/wiki/spaces/PMT/pages/4031676438/CheckList+Field+Documentation \ ./implementation-plan-PROJ-123-2026-02-15.md \ --thoughts "Added bulk delete endpoint, updated the update endpoint for partial updates"
→ doc-review-2026-02-15-143025.html then Confluence page updated

Minimal (no thoughts)

New
▶

The --thoughts flag is optional. The command still works by analyzing the plan and codebase.

/documentation --new https://planradar.atlassian.net/wiki/spaces/PMT/folder/4040359987 \ ./implementation-plan-PROJ-123-2026-02-15.md
FlagDescription
--new <folder-url> Create a new page under this Confluence folder (triggers New mode)
--thoughts <text> Optional context about what was implemented or what's important to document

/full-cycle

Pipeline

Orchestrates the entire development lifecycle in a single automated pipeline — requirements analysis, planning, implementation, code review, and documentation — with a live HTML master dashboard tracking all 5 stages.

Single ticket

▶

Run the full pipeline for a single Jira story. All 5 stages execute automatically, pausing only at critical decision points.

/full-cycle PROJ-123
→ full-cycle-2026-02-15-143000.html (master dashboard)

Multiple tickets

▶

Run the pipeline across multiple Jira stories at once.

/full-cycle PROJ-123 PROJ-456 PROJ-789

Sprint

▶

Run the full pipeline for all stories in a sprint.

/full-cycle "Sprint 5"

Tickets + Figma designs

▶

Provide Figma URLs explicitly for design analysis in Stage 1.

/full-cycle PROJ-123 PROJ-456 \ --figma https://www.figma.com/design/abc/File1

Full combo with linked tasks

Recommended
▶

The full command: multiple tickets, linked task inspection, and explicit Figma files. This gives the most thorough end-to-end result.

/full-cycle PROJ-123 PROJ-456 \ --check-linked-tasks \ --figma https://www.figma.com/design/abc/File1
→ full-cycle-2026-02-15-143000.html + all stage artifacts
FlagDescription
--figma <urls> One or more Figma file URLs to analyze against the Jira stories
--check-linked-tasks Also fetch linked issues, subtasks, priority, and status for each story

Pipeline Stages

1. Requirements Analysis — fetches Jira + Figma, maps stories to designs, detects mismatches, publishes to Confluence
2. Implementation Planning — generates a phased plan from Jira + Confluence + analysis context
3. Implementation — architecture discussion, then phase-by-phase code + tests (uses /implement-plan-nicely workflow)
4. Code Review — reviews all changes, generates interactive HTML report, applies selected fixes
5. Documentation — creates or updates Confluence API documentation from code + plan

Pause Points

The pipeline auto-continues where safe and pauses only at critical decisions:

Unmapped stories/designs Before plan generation Architecture decisions After each phase Review results Doc target selection

Master Dashboard

✓ Complete ↻ Active ⏳ Pending ✗ Failed ⏸ Paused

A single HTML dashboard tracks all 5 stages, sub-steps, decisions log, and all artifacts produced. Updated after every significant event. Dark theme with collapsible stage cards, progress bar, and color-coded status indicators.
